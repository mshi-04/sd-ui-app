# コメント

このルールはリポジトリ全体へ適用する。
`app/src/main` の Kotlin だけでなく、Gradle スクリプト、version catalog、
AndroidManifest、リソース、その他の設定ファイルも対象とする。

## 本番コードと設定ファイル

`app/src/test` と `app/src/androidTest` を除くすべてのファイルで、
字面から読み取れる説明をコメントに書かない。
説明を書きたくなったら、まずコードで表現できていないという合図として扱う。
Kotlin では名前、値オブジェクト、早期リターン、関数の分割で意図を表す。
設定ファイルでは key、task 名、alias 名で意図を表す。

字面から読み取れない事情に限り、1 行で書いてよい。

- 排他制御、実行順序、冪等性など、呼び出し側から見えない並行性の制約
- 一見すると不具合に見える意図的な挙動や、外部都合による workaround の理由
- ツールや法的要件が要求するもの（`@Suppress` の理由、ライセンス表記など）
- 依存の pin に添えるバージョン注記。更新ツールが更新の判断に使う

背景・トレードオフ・採用しなかった案は PR の説明か `docs/` へ書き、コードには残さない。
サーバー契約、検証コマンド、命名規約といった運用方針も同じ扱いとし、
[`docs/server-contract.md`](../../docs/server-contract.md) と
[`docs/development-setup.md`](../../docs/development-setup.md) を正本とする。

## テストコード

`app/src/test` と `app/src/androidTest` に書く基本のコメントは次の 2 種類。

1. AAA ラベル: `// Arrange` / `// Act` / `// Assert` / `// Act & Assert`
2. 検証観点: `// Act` または `// Act & Assert` の直下に 1 行

検証観点は **英語** で書く。

```kotlin
// Act
// Boundary: blank status is rejected
```

これに加えて、テスト対象の仕様や外部要因に由来する前提だけ書いてよい。
MockWebServer の応答順、Retrofit の復号失敗が例外になることなど、
テストコードを読んでも導けない根拠が対象になる。前提も英語で書く。

検証観点は `// 観点: Normal - ...` のような別形式で書かず、上記の `// <観点>: <意図>` に統一する。
AAA ラベルへ説明を足した `// Assert: ...` も使わない。

値の意図はテスト関数名と検証観点で表し、fixture の説明やヘルパー関数の KDoc は書かない。

観点の種類と命名規則は [`docs/unit-test.md`](../../docs/unit-test.md) を正本とする。

## 適用範囲

このルールは新規のコードと設定、および実質的に変更するコードと設定へ適用する。
既存ファイル全体は、意図した移行作業でない限り一括変更しない。

## 実装前の確認

新規ファイルを追加する前に、同じ package またはディレクトリの既存ファイルを開いて記述の粒度を確認する。
